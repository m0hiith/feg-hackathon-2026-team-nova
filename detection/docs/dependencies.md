# Dependencies and declarations

_Versions below are the ones actually installed and used to produce every number
in `docs/`. Verify with `.venv-ui/bin/pip list`._

## 1. Runtime dependencies

The pipeline (`src/`) is **Python 3 standard library plus one package.**

| package | version | licence | used by | role |
|---|---|---|---|---|
| **duckdb** | 1.5.5 | MIT | `src/replay.py`, `src/features.py`, `src/trigger.py`, `scripts/*.py` | Reads the event parquet/CSV and does all set-based aggregation. The only runtime dependency. |

Standard library only, everywhere else: `argparse`, `collections`,
`dataclasses`, `datetime`, `enum`, `hashlib`, `importlib`, `json`, `pathlib`,
`random`, `re`, `sys`, `types`, `typing`, `__future__`.

**There is no ML dependency.** No scikit-learn, no PyTorch, no TensorFlow, no
XGBoost, no LLM API. The trigger is rule-based (`docs/architecture.md` §4);
there is nothing to train and nothing to serve.

**The demo UI has no runtime dependency at all.** `src/ui/index.html` is one
self-contained file — no build step, no CDN, no framework, no external script or
stylesheet. It opens on `file://`.

## 5. Finding: the Android screen-name instrumentation gap

**Recorded as a data-quality finding, because it limits the product and the fix
is on FEG's side.**

`fortuna_screen_name` is the column that names the screen a user is on. It is
the only such column on the three app platforms (`SCREEN_SOURCE` in
`src/features.py`; GM and web resolve screens from `page_location` instead).

### Measured coverage

Over `data/clean/events.parquet`, restricted to view events
(`screen_view`, `page_view`, `fortuna_screen_view`) — the denominator
`features.py` itself uses for `screen_coverage`:

| platform | view events | screen name populated | **coverage** | players |
|---|---|---|---|---|
| **SB iOS** | 57,105 | 57,105 | **100.0%** | 21 |
| **SB Android** | 103,636 | 40,543 | **39.1%** | 20 |
| **Casino Android** | 31,353 | 2,148 | **6.9%** | 21 |
| GM | 66,342 | 0 | 0.0% | 83 |
| web | 5,085 | 0 | 0.0% | 9 |

iOS names the screen on **every single view event**. SB Android names it on
**39.1%**. Casino Android names it on **6.9%**.

### It is an SDK omission, not a version split — with a correction

An earlier draft of this finding claimed the rate was *flat* across all 20
Android players. **That is not what the data shows and the claim is withdrawn.**
Measured per player (≥100 view events):

- **SB Android:** 14.0% – 46.2%, a **32.2-point spread** across 19 players.
- **Casino Android:** 0.1% – 19.8%, a **19.7-point spread**.

The rate is **not** flat. The conclusion nevertheless holds, on two other pieces
of evidence that were measured to test it:

1. **Every Android player is affected, and none is complete.** 20 of 20 SB
   Android players have incomplete screen naming; the best-instrumented player
   still reaches only 46.2%. A version split would show some players near 100%
   and others near 0%. Nobody is near 100%.
2. **There is no step change over time.** Daily coverage across the 31-day
   window runs 34.0% – 42.5%, an 8.5-point spread with no discontinuity. A
   staged app-version rollout would produce a visible step as users updated.
   There is none.

Together these point to **specific screens never emitting the field on Android**
— a partial SDK instrumentation gap affecting every user on every build — rather
than a subset of devices running old code. The per-player variation is then just
a consequence of which screens each user happens to visit.

### The gap is unrecoverable downstream

On the 63,093 SB Android view events missing `fortuna_screen_name`, **no other
locator column is populated at all** — `on_route`, `from_route`,
`page_location`, `page_referrer`, `on_origin`, `on_origin_name`, `from_origin`
and `game_name` are **0.0% populated** on every one of those rows. The event
records that a screen was viewed and nothing whatsoever about which screen.

**No downstream fix is possible.** `resolve_screen()` returns `None` and
`features.py` deliberately does *not* fold unnamed screens into a shared
"unknown" bucket, because that would make every unnamed screen look like a
revisit of every other one and **manufacture a back-and-forth signal that is not
in the data**. Honest absence is preferred to fabricated presence. Every feature
dict reports `screen_coverage` so any consumer can see how far to trust the
screen features, and `MIN_SCREEN_COVERAGE_TO_TRUST = 0.90` in `src/trigger.py`
flags them as untrusted below that line — which is every Android session.

### The fix, and what it would unlock

**The fix is on the client:** populate `fortuna_screen_name` on every
`screen_view` event on SB Android and Casino Android, as the iOS SDK already
does. It is an instrumentation change, not an analysis one, and no amount of
downstream work substitutes for it.

**What it would unlock.** The back-and-forth signal — `repeat_screen_events`,
a user bouncing between screens while holding an unplaced slip — is currently
**computed and carried as evidence on every decision but never allowed to fire
on its own** (`BACK_AND_FORTH_EVENTS = 12` in `src/trigger.py`). It is held back
for two reasons, and the instrumentation gap is one of them:

1. **Measured cost.** A back-and-forth firing path was tested at thresholds
   8/12/20 and **rejected**: it lifted recall to 55% but cut precision from
   37.4% to 31.9% (`src/trigger.py` docstring).
2. **It cannot be trusted where it is most needed.** On Android the signal is
   built from 39.1% and 6.9% of the evidence, so a low `repeat_screen_events`
   count is indistinguishable from a well-instrumented user who simply did not
   backtrack.

With full Android coverage, (2) disappears and (1) becomes re-testable on honest
data. This matters directly for the result in `docs/impact-case.md` §3, where
**SB Android is the platform the trigger performs worst on (0.91x lift, below
base rate)** — and where the strongest unused behavioural signal is also the
least observable. Whether those two facts are related is exactly what this
dataset cannot answer.
