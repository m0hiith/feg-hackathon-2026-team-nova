# Synthetic Player Dataset — FEG Hackathon 2026

**Challenge 1: Session Quality & Session-to-Action Conversion**

All data in these files is **synthetic and generated by script**. No real player data,
no real identity documents, no production feeds. Every PlayerID is prefixed `SYN_Uxx`
and every row carries `is_synthetic = True`. Reproducible with seed `20260908` via
`tools/generate_synthetic_users.py`.

> **v2 (odds-aware).** This dataset was regenerated to make odds *movement* real.
> See "The odds model" below and `docs/odds-model.md`. The v1 files as originally
> delivered are preserved untouched in `files/`.

engine code runs on both files without changes.

Three synthetic-only columns are appended and clearly marked:

## The odds model (new in v2)

v1 drew a fresh random `selection_id` for every `betslip_add_bet`. The same
selection was therefore almost never seen twice — 10,411 distinct ids across
10,421 rows — so odds movement could not be computed at all, and the project's
hard rule ("never show only favourable odds movement; if odds got worse, say so")
had nothing to compute from.

v2 introduces a market book:

- **Fixtures are stable.** A competition gets one fixture per 3-day bucket, with a
  kickoff. Sessions in the same bucket see the same fixture.
- **Selections are stable.** Each fixture owns a fixed set of `(market, outcome)`
  selections with SHA-256-derived ids, reproducible across processes.
- **Odds are a function of time.** `odds_at(selection_id, t)` is a per-selection
  sine wave plus a small linear trend. Same selection + same instant → same price;
  a later instant → a different price, drifting in **both** directions.
- **Abandoned slips can be resumed.** An abandoned slip is remembered, and a later
  session may rebuild that exact slip while the fixture is still open. That second
  observation is what makes an honest movement card computable.
- **Placed bets reuse the added selections.** v1 re-randomised `selection_id` on
  `betslip_placed_bet`, so a placed bet could not be linked to the bet added. In v2
  all 4,168 placed selections match an added selection.

### What that yields

| Property | v1 | v2 |
|---|---|---|
| Selections observed more than once | ~0 | 3,951 |
| Selections carrying >1 distinct price | 5 | 984 |
| Observed price movements | — | 963 |
| …of which **worse** for the player | — | 483 |
| …of which **better** for the player | — | 480 |
| Slips resumed in a later session | — | 578 |

Movement is near-perfectly balanced by construction, not by tuning: the sine phase
is drawn per selection and the trend sign is symmetric around zero. An engine that
only surfaced favourable moves would be visibly cherry-picking, which is exactly
what the hard rule forbids.

## How this delivers the click reduction

`synthetic_user_profiles.csv` holds, per user: `top_sport`, `top_competition`,
`top_game`, `usual_betslip_type`, `usual_stake_eur`.

Every one of those is something the product currently makes the user find or type.
The engine derives them from history, so the home page can open with them
already filled:

**Today**

```
open → homepage → sports → league → match list → match detail
     → select market → betslip → type stake → confirm
```
Roughly 8–9 taps plus typing.

**With the engine**

```
open → "Continue" card (competition + market + slip type + stake pre-filled)
     → confirm
```
2 taps, zero typing, zero search.

Same on casino: `top_game` + `provider` gives a one-tap resume instead of
browsing the lobby.

Measure it in the demo as **taps-to-action** and **time-to-first-action**, both
official Challenge 1 metrics.

## What is deliberately NOT in here

No names, emails, ages, locations, payment instruments, card data, IP addresses
or device identifiers. Nothing that would need a DPIA. The engine is trained on
behaviour inside the product only, which is the argument made in
`docs/compliance-note.md`.
